# 后续战略方向评估

> 评估日期: 2026-07-29 | 当前状态: HTTP P50=29μs, P99=73-699μs, 吞吐 220k req/s

## 一、三项方向可行性与必要性

### 方向A: SO_REUSEPORT 多进程

| 维度 | 评估 |
|------|------|
| **可行性** | 极高。Linux 内核原生支持，`setsockopt(SOL_SOCKET, SO_REUSEPORT)` 一行代码 |
| **必要性** | 高。多线程 accept 已改善 P99 51-79%，多进程可进一步线性扩展 |
| **实现量** | ~50 行。fork() + 每进程独立 io_uring ring + 已有 accept 逻辑复用 |
| **风险** | 低。零共享状态，进程隔离天然无锁 |
| **收益** | N 进程 → 每进程承载 conns/N → P99 等比下降。4 进程时 64 连接 P99 从 2.6ms → ~700μs |

**nginx 的做法**：fork N 个 worker 进程，每个 `SO_REUSEPORT` accept，零共享内存。这是工业界最成熟的水平扩展方案。

### 方向B: 大消息零拷贝完善

| 维度 | 评估 |
|------|------|
| **可行性** | 已实现（ring slow path 多 segment 零拷贝 + 16KB buffer） |
| **必要性** | 中。64KB HTTP 响应 P50=133μs, 吞吐 4.75GB/s——已接近线速。256KB 响应 P50=370μs |
| **剩余工作** | 256KB+ 响应场景边缘优化，投入产出比低 |

### 方向C: HTTP/2 多路复用

| 维度 | 评估 |
|------|------|
| **可行性** | 低。需要完整实现 HPACK/QPACK 头部压缩 + 流控制 + 优先级树，~5000+ 行 |
| **必要性** | 中。多路复用可减少连接数→间接改善 P99，但实现成本极高 |
| **结论** | 独立大项目，不适合当前 sprint |

## 二、优先级排序

```
P0: SO_REUSEPORT 多进程  ← 立即执行（高收益、低风险、低代码量）
P1: 大消息 >256KB 优化   ← 后续（需求驱动）
P2: HTTP/2              ← 独立项目（需要完整协议栈）
```

## 三、P0 实施方案：SO_REUSEPORT 多进程 HTTP 服务器

### 实现

1. 主进程 fork() N 个子进程（N = CPU 核数）
2. 每个子进程创建独立的 `Launcher` + io_uring ring
3. 所有子进程对同一端口设置 `SO_REUSEPORT`
4. 每个子进程独立 accept + 处理 HTTP 请求
5. 内核自动将连接均匀分发到各进程

### 测试矩阵

| 进程数 | 总连接数 | 预期每进程 conns | 预期 P99 |
|--------|---------|----------------|---------|
| 4 | 64 | 16 | ~700μs |
| 4 | 128 | 32 | ~1.5ms |
| 8 | 64 | 8 | ~300μs |
| 8 | 256 | 32 | ~1.5ms |

### 验证标准

- 64 连接 × 8 进程: P99 < 500μs
- 无进程间数据竞争 (ASAN clean)
- 吞吐量线性扩展（8 进程 ≈ 8× 单进程）
